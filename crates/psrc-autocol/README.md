
# autocol

A schema-free auto-columnar transform: a reversible, bit-exact pre-pass that makes general
compressors (zstd, brotli) 15–50% smaller on structured, line-oriented data (logs, CSV,
JSONL, telemetry). It discovers record structure with no schema and reorganizes rows into
per-column streams.

This is not a compressor. You run it before your compressor: the output goes to
zstd/brotli/xz as usual, and a safe gate ensures the result is never worse than the best
plain codec.

## How it works

1. Split input on newlines into records.
2. Tokenize each record into whole `[A-Za-z0-9]+` tokens and the separators between them
   (hex/uuid stay whole, so no template explosion).
3. Group records by skeleton (separator sequence). Within a group, token positions that
   are constant fold into a template; positions that vary become columns.
4. Pack `[templates][record→template ids][columns]` into one stream, so the backend sees
   per-column-homogeneous data (all status codes together, monotone timestamps
   delta-coded). Numeric columns get a zigzag-varint delta transform.

The win comes from per-column homogeneity plus single-stream packing: one backend call
amortizes per-stream overhead. `decode(encode(x)) == x` always (B009-verified).

## Benchmarks

Ratio = `compressed / original` (lower is better). Baselines are zstd -19 and brotli -q11
(the strongest standard settings). `ac→zs` / `ac→br` are the same backends run on the
transformed blob. `eff` = `min(zstd, brotli, ac→zs, ac→br)`, the safe-gated result you'd
actually ship. `win%` = `eff` vs the best plain codec. Every file is verified bit-exact.

best plain codec on every out-of-scope file (never larger), and the run STILL netted +5.8% 
overall with all numbers inclusive, carried entirely by the logs. The transform targets 
line-oriented text; on everything else it is a measured no-op rather than a regression.

### Where it doesn't help: a random home-directory sample

A seeded random sample of 40 files from a developer home directory: source code.
Some markdown, configs (`.ts`, `.py`, `.rs`, `.go`, `.md`, `.tsx`), plus a 
couple of binaries (`.pyc`, git `.idx`, cache blobs).

0 of 40 beat the best plain codec, and 0 of 40 lost. Free-form text and code have no
record skeleton, so the transformed blob compresses worse (`ac→brotli` ran about 40–60%
larger than plain). The safe gate fell back to the best plain codec on every file: net
0.0% saved, 0.0% lost, all bit-exact.

That is the boundary: autocol is a specialist for line-oriented, record-structured data
(logs, CSV, JSONL, telemetry, SQL). On general files it is a measured no-op. Don't point
it at a source tree expecting wins, but it won't make anything larger if you do.

### String-heavy tables, Parquet, and the "pre-tokenization" question

Tested against a real Parquet export: a 167-row × 27-column `companies` table, mostly
string columns (names, domains, URLs, locations). Ratios vs the CSV (raw text) form:

| approach                                      | ratio |
|-----------------------------------------------|---------|
| Parquet, re-encoded brotli-11 (max)           | 0.509 |
| plain brotli -q11 on the CSV                  | 0.216 |
| autocol → brotli (gate falls back)            | 0.250 |
| per-column dictionary "tokenization" → brotli | 0.208 |

// Each a case where it does not help:

- Plain brotli beats Parquet about 2.4× here (and about 15× on a 14-row table). These
  exports are small: the Parquet footer alone is 25–67% of the file. Parquet needs
  MB-scale data to amortize its metadata; below that, a general compressor on the raw
  text wins outright.

- autocol falls back. A string table isn't numeric or templated, so the columnar split
  doesn't help and the gate ships plain brotli: never worse, never better.

- Pre-tokenization barely helps. Per-column dictionary encoding (replace repeated values
  with IDs, the classic tokenization move) gained only about 3%. Half of the 27 columns
  are low-cardinality or constant, but brotli's LZ stage already deduplicates them for
  free: those 9 non-unique columns compress to 110 B, 0.6% of the total. The other 99% of
  the bytes are high-cardinality unique strings (URLs, names, IDs, traffic numbers)
  already near the entropy floor, which no dictionary or tokenizer can shrink.
  Tokenization is redundant with a general compressor's LZ on repeated data, and powerless
  on unique data.

## Net Result:  

We have found, and even though there may be other cases where beneficial, 
it holds that autocol's edge is: numeric, timestamp, and structured logs and metrics. 

Not generic string tables. Not free transforms alone. Plain Brotli already handles those 
better than both autocol could and, at these sizes: Parquet too. But, it will serve well.


## Reproduction

The numbers above come from `psrc-corpus`, the benchmark harness of the PSRC research
workspace this crate grew out of; the harness and its generated corpus are not published
with the crate. To check the claims independently: take your own line-oriented corpus
(logs, CSV, JSONL), compress each file with plain zstd, then with autocol -> zstd — the
[`mkz`](https://crates.io/crates/mkz) CLI does exactly this, never-worse gate included —
and compare sizes. Ratios are independent of build profile: the transform output is
byte-deterministic and the compression backends are external.

## Caveats
- The transform seemingly only helps w/ line-oriented, record-structured data. On binary, 
  or other non-line-delimited formats it does nothing really useful, but having the weighing 
  gate means the output is never larger than the best plain codec. 
- The numeric-column codec is a simple "delta if canonical integer, else raw" heuristic. 
  A measured per-column codec menu (dictionary, RLE, delta-of-delta) would likely squeeze
  more; it is not implemented yet but on roadmap for verify.
- Re: `--autocol` try comparing `backend(blob)` vs `backend(whole)`. 
- Still looking for that elusive free-form-text win; so far a general compressor still owns that ground.
